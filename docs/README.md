## 当前实现

- 管理员登录后进入 `#/admin/catalog/sources`，侧栏只有「商品 → 源商品库」。OPPO 和一加分开导入，支持暂停后续跑、按品牌和关键词分页查询已入库原文。[管理员工作台](architecture/admin-workspace.md)
- 后端已实现吉客云只读查询、单品牌任务和七字段落库。两品牌真实请求均成功且样本七字段非 NULL；自动清洗和标准目录待接入。[商品查询与同步方案](architecture/catalog-admin-design.md#单页查询联调)
- 飞书客户端自动免登，失败可手动重试。浏览器可扫码、刷新二维码或跳转网页授权。已在本机看到飞书官方二维码，扫码回调和会话恢复已通过模拟验证。真实手机确认后的登录待联调。[飞书登录验证记录](architecture/feishu-auth-flow.md#验证记录)

## 当前数据库基线与重设计约定

项目处于第一开发阶段，所有表都可以按生产级 MySQL 标准重新设计。每次重设计前，先说明拟调整范围、原因及数据和代码影响，再向用户重新确认。收到明确同意后开始设计和实施。[项目约定第 13 条](../AGENTS.md#3-核心技术规则与边界)

查库、变更和验证所需 SQL 保存为 `docs/sql/` 下的 `.sql` 文件，由用户在 Navicat 执行。

当前九表基线包含商品同步、标准规格、独立规格颜色及政策颜色范围。首次建表由用户在 Navicat 执行空库 SQL。本机项目库已执行旧版九表，核对时商品导入任务、来源和商品操作日志均为空，可用[增量脚本](sql/upgrade_empty_goods_sync_to_single_brand.sql)升级到单品牌任务。

品牌仅一加手机和 OPPO手机，来源只采集七业务字段；原始字段先入库，再自动清洗系列、型号、配置、颜色，明确规则唯一结果自动入可用标准库，缺失/歧义/冲突才人工审核。颜色不要求逐个手工建。当前结构将候选、证据、规则版本、异常、审核及映射放在来源表，任务分开记录导入和清洗阶段，日志区分 SYSTEM/USER。`skuId` 用于续拉，两品牌各自记录最新进度。清洗接入状态见上方「当前实现」。

## 仍需确认或联调

1. 吉客云已实测两品牌的 brandName 筛选、result.data 数组和 lastMaxId 续拉。末页结束条件、最大页大小、限流额度和包含停用商品的场景仍需联调。首期不存外部商品身份，因此采用全量内容比对，不承诺可靠 SKU 增量或完整历史批次回放。
2. 数量为 0 的业务含义、固定补贴上限范围、比例精度/范围、金额舍入与计算基数来源。
3. 时间端点、覆盖优先级、不同政策不限颜色与指定颜色交集的替换、旧政策恢复、局部生效及后续新增颜色对既有政策的适用规则。颜色范围本身已明确，不再把空颜色是否通配列为未定：必须用 color_scope 表达。
4. 管理员名单、跨人可见范围、自审及拒绝原因要求；默认不扩大租户范围。
5. 附件、备注及链接必填要求和权限、容量；实际部署域名及多实例会话。
6. 用真实手机扫码确认，核对当前角色入口及会话刷新。回归飞书内免登和网页授权，并在部署地址确定后核对重定向配置。[飞书真实联调步骤](architecture/feishu-auth-flow.md#浏览器真实联调步骤)
