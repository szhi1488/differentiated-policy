# 差异化政策管理文档库

更新日期：2026-11-14。项目指令见 [AGENTS.md](../AGENTS.md)，启动和配置见 [项目 README](../README.md)。

## 当前实现

- 管理员登录后进入 `#/admin/catalog/sources`。右上角「导入商品」弹窗支持选品牌、全量或按建档日期导入。可在弹窗续跑和查看该日商品，列表按品牌、建档日和关键词筛选，并分别显示 SKU 与商品修改时间。[管理员工作台](architecture/admin-workspace.md)
- 吉客云导入按 SKU 更新原文，支持全量、按建档日和按修改日。管理员在「商品清洗与识别」按品牌和日期预览 SKU，二次确认后手动发起。结果页默认汇总两个品牌，清洗记录可查进度和结果统计。商品审核保留系列、型号、配置、颜色四项，直接点通过或不通过，无需填写原因。[管理员工作台](architecture/admin-workspace.md) · [商品管理接口](api/catalog-api.md)
- 管理员可从「商品 → 商品中心」按品牌、系列和机型浏览标准商品，使用即时下拉筛选，手工新增、编辑或删除未被引用的商品，并维护品牌、系列和颜色字典。商品编辑已接通保存，支持版本冲突提示和引用保护，使用现有十四表基线。[商品中心](architecture/admin-workspace.md#商品中心) · [商品编辑接口](api/catalog-api.md#商品编辑)
- 系列下的机型没有商品或政策明细引用时，管理员可给系列改名或删除，删除时一并清理无引用机型。[商品数据字典](api/catalog-api.md#商品数据字典)
- 飞书客户端自动免登，失败可手动重试。浏览器可扫码、刷新二维码或跳转网页授权。已在本机看到飞书官方二维码，扫码回调和会话恢复已通过模拟验证。真实手机确认后的登录待联调。[飞书登录验证记录](architecture/feishu-auth-flow.md#验证记录)
- 「提交政策」读取在售目录。两个抽屉都支持配置多选和「全部配置」，全选范围由当前品牌、系列和机型决定。普通卡跨页勾选所选配置的在售商品，可取消单项。指定卡单选商品，数量按平台选填。草稿可通过保存后的申请地址回填，提交按实际适用平台写入最终勾选的商品 ID。[动态表单](business/perspective-rules.md)
- 「我的提交」`#/apply/submissions` 分页查询本人的草稿和提交记录，支持状态、渠道和整单平台筛选。详情显示各轮审核结果、意见和提交快照。草稿和已驳回申请可继续编辑，驳回重提沿用原单号并保留旧轮次。待审核和已通过申请只读。[申请人政策接口](api/policy-api.md)

## 当前数据库基线与重设计约定

项目处于第一开发阶段，所有表都可以按生产级 MySQL 标准重新设计。每次重设计前，先说明拟调整范围、原因及数据和代码影响，再向用户重新确认。收到明确同意后开始设计和实施。[项目约定第 13 条](../AGENTS.md#3-核心技术规则与边界)

查库、变更和验证所需 SQL 保存为 `docs/sql/` 下的 `.sql` 文件，由用户在 Navicat 执行。

本项目是嵌入飞书的公司内部 ERP，所有有效管理员共用同一套商品数据。十四表空库基线使用 `brand`、`series`、`spu`、`color_dict` 和 `goods` 保存公司共用标准目录。来源映射具体标准商品，政策以实际选中的商品 ID 确定适用商品，机型加 RAM、ROM 用于配置查询。商品目录、导入、源商品、清洗及政策明细均省去租户标识。源商品仅按吉客云 SKU ID 唯一匹配，源内容未变时保留原商品和清洗结果。商品链路已接入原基线。由用户在 Navicat 对空库执行建表脚本二选一。[数据字典](sql/database-design.md)

来源保留原始七字段、SKU ID、完整分类路径、两种修改时间和状态标记。建档日取自按日导入命中或可追溯的旧任务。原文先入库，再经管理员确认后按当前代码识别系列、型号、配置和颜色，明确结果自动入标准库。清洗和审核通过写入或复用 `goods`，同时回填来源映射。候选、证据和当前映射保存在来源表，独立清洗任务固定本轮 SKU 和结果。商品导入记录继续支撑建档日查询，新基线不保存清洗日志。[商品表关联示例](sql/database-design.md#商品表关联示例) · [商品同步方案](architecture/catalog-admin-design.md) · [商品清洗细则](business/catalog-cleaning.md)

政策三表已确认并写入空库 SQL。`policy_apply` 保存当前表单，`policy_audit_log` 保存各轮快照和审核结果，`policy_goods_detail` 保存按轮次展开的商品范围。草稿、提交、本人列表与历史查询及商品中心引用检查复用这三张表，目标 MySQL 待联调。[政策三表](sql/database-design.md#政策三表)

## 仍需确认或联调

1. 吉客云已实测两品牌的 `brandName` 筛选和 `lastMaxId` 续拉。目标 MySQL 上的全量导入额度、停用来源覆盖、清洗及标准商品维护待联调。完整批次回放待设计。
2. 数量为 0 的业务含义，固定及比例补贴上限、实单仅填上限的含义、平台名称映射、比例精度与范围、金额舍入及计算基数来源。[实单与待确认口径](business/perspective-rules.md#实单与待确认口径)
3. 时间端点、覆盖优先级、旧政策恢复和局部生效。普通卡和指定卡均只覆盖已选商品，按平台和商品 ID 检查交集。
4. 管理员名单、跨人可见范围、自审及拒绝原因要求；默认不扩大租户范围。
5. 附件、备注及链接必填要求和权限、容量；实际部署域名及多实例会话。
6. 用真实手机扫码确认，核对当前角色入口及会话刷新。回归飞书内免登和网页授权，并在部署地址确定后核对重定向配置。[飞书真实联调步骤](architecture/feishu-auth-flow.md#浏览器真实联调步骤)
7. 目标 MySQL 上联调本人筛选、草稿回填、历轮快照及跨账号隔离。真实审核到驳回重提的联调待管理员审核接入。已有 H2、MockMvc 和模拟接口浏览器结果见[我的提交验收记录](architecture/frontend-development.md#2026-11-14-我的提交接口接入)。
