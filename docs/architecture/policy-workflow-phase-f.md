# F 阶段交付与切换手册

2026-11-24。P27–P30 已接入 ERP 投递队列，P31 已完成本地回归。P32 获准向指定测试群验证连通性。用户后来提供的群截图也记录了平台交接和政策审核通知。完整试点和正式切换仍待现场验收。

## 执行期和收件规则

| 事件 | 登记与发送口径 |
| --- | --- |
| 开始执行 | 采购批准当秒已经采用的范围并入终审群结果。未来开始的政策到起点按商品与平台回放，百亿沿用平台与配置规则。迟到投递同时核对起点和当前采用情况。只在旧单被采用的范围不报新单生效。群中点名相应平台现负责人。 |
| 临期私聊 | 已通过政策按实际截止的北京时间日期计算，提前两个自然日、一个自然日分别在 17:00 提醒一次。机器人私发该政策原申请人，平台移交后收件人仍是原申请人。详见[时间示例与补送](#原申请人的临期私聊)。 |
| 到达截止 | 每张政策使用原单最新获批的实际截止。截止事件从实际截止的下一秒起发群提醒，点名原申请人及受影响现负责人，按人去重。原申请人停用时，有有效接手人仍可送达。 |
| 切换与补送 | 启用或重启扫描当前仍有效及未来已批的政策，包括独立改期和随单改期后仍有效的原单。首次启用跳过此前已结束的政策。恢复时重新核对各项的发送时窗。临期私聊按企业、政策和提醒日期防重，群内的执行期提醒沿用各自的事件标识。 |
| 截止变更 | 独立调整确认或随单调整获批时，按目标原单在同一事务内更新截止、留存记录、登记改期群通知，并重算后续提醒。拟定提前截止已过时保护历史至批准前一秒。群消息点名原申请人、涉及平台的现负责人和本次办理人。提前结束时列调整前完整政策时段、前后截止与原因。 |
| 延期 | 随单延期尚待审核或被退回时，原单沿用最近一次获批日程。获批后，原单改期通知写明本次调整前截止、新截止、接续起点和原因。接续起点取前次实际截止的下一秒与本次办理时刻中较晚者，已中断的时段按真实时间保留。后续再调整仍使用同一原单。 |
| 平台交接 | 平台分工保存成功后，按渠道和平台登记。现有页面先释放再分配，释放时通知待分配，接任时注明前后负责人。停用或升为管理员引起的释放也登记。相同分工重复保存不新增提醒。退回修改仍归原申请人。 |
| 商品导入异常暂停 | 按批次及暂停版本登记，群通知列出批次和失败原因并点名发起人。已续跑的旧暂停失效。发送前核对发起人账号及导入权限，无法解析时保留失败记录供核对。 |

采购在「商品清洗与识别」查看清洗结果并处理待审核或技术失败的商品。清洗任务结束时不发送飞书群通知。

后台将延期、临期、交接、商品导入异常暂停、审核卡和个人待办的投递结果写入 `policy_review_delivery`。排查时可在 Navicat 核对下次尝试时间、实际飞书回执和失败原因。发送器按事件的重试规则处理可重试失败。[后台投递记录](../api/policy-review-settings.md#后台投递记录)

群截止通知以该单最近一次生效的截止时刻登记，在截止的下一秒到期。已发消息按原投递记录核对回执。

### 原申请人的临期私聊

以实际截止日为 D。假设政策 ZC-000027 的实际截止是北京时间 2026 年 12 月 9 日 12:00，机器人按下表向原申请人私发橙色只读卡「政策临期提醒」。

| 私聊发送时间（北京时间） | 卡片正文示例 |
| --- | --- |
| 12 月 7 日 17:00（D−2） | ZC-000027 将于后天到期，实际截止 2026-12-09 12:00:00（北京时间）。 |
| 12 月 8 日 17:00（D−1） | ZC-000027 将于明天到期，实际截止 2026-12-09 12:00:00（北京时间）。 |

同一张政策即使涉及多个商品或平台，每个提醒日仍只私发一次。群内演示样例只用于核对格式。正式临期通知的自动收件人始终是原申请人。超过实际截止后，按上表单独发送截止事件群通知。

如果在提醒当天 17:00 后才获批或服务才恢复，当日尚可补送。跨到下一自然日后，已错过的那一日不再补发。比如 12 月 8 日上午恢复服务，当天 17:00 只发 D−1 提醒。发送前重新核对实际截止。若获批缩短后的提醒日期与原计划有一天相同，当天沿用同一条记录并按新截止发卡，已经送达时不重发。过时的计划失效。原申请人账号无法接收时，管理员核对该项投递记录。

### 群消息与投递编号

后端重启加载新版后，新群消息显示业务摘要，并按需 @ 收件人。投递状态和飞书回执保存在 `policy_review_delivery`。发送请求继续携带同一个 UUID 防重。此次正文调整无需改表，已有群消息上的编号仍可用于核对历史回执。[后台投递记录](../api/policy-review-settings.md#后台投递记录)

## P33 切换、暂停与恢复

1. **核对目标库。** 新空库由用户在 Navicat 执行一份完整基线。已有业务数据的目标库核对 `policy_review_delivery` 的个人卡片收件人约束、独立提醒的空政策编号和 `notice_key` 唯一性，并核对投递记录及回执。[空库建表步骤](../sql/database-design.md#1-在-navicat-建表) · [工作流七表字段](../sql/database-design.md#工作流七表字段)
2. **部署前**，分别核对测试和正式的企业、应用、业务群、网页应用的桌面端与移动端主页、来源白名单、服务器北京时间与手机可达性。管理员在 ERP 核对品牌采购和品牌或系列的初审人、当前轮次的冻结指派及自审排除。确认机器人在群内，具备发送、读取消息、验证群成员及 Task V2 所需权限。按部署模式核对长连接或 HTTP 卡片回调。[部署参数](environment-configuration.md) · [卡片回调及权限](policy-workflow-phase-e.md#环境配置与目标库)
3. **启用**，先完成现场联验并留存目标 MySQL 核对结果。将使用同一队列的实例部署为同一版本，设置 `POLICY_REVIEW_DELIVERY_ENABLED=true` 后重启。初始化时按当前有效期登记执行期提醒。已送达、发送中及结果待核对的投递保留原记录。默认每 3000 毫秒领取一项到期动作。检查近期业务提醒、最长待发时间、已失效项、失败和结果未知项，再对照飞书回执。临期私聊只补送当日 17:00 后仍符合条件的那一份。
4. **暂停**，在所有投递实例关闭上述开关并重启，核对停机前已经发出的请求。保持 ERP 和卡片回调在线。已发卡仍可签署，原流程的按轮指派继续决定采购权限。新建卡、卡面更新、结果群通知和待办在队列等待。已登记原单的截止调整仍更新原计划。
5. **恢复**，核对企业、目标群、原群回执、当前轮次和成员，在同版本实例恢复开关。已有回执继续保留，旧指派和过时提醒在发送前再核验。发送结果未知且超出幂等窗口的项保留在数据库，供核对飞书实际收件。
6. **应用版本回退**，优先暂停外发。需回退至 E 版时先停止 F 版实例，保留扩展后的表结构、所有登记和回执，并在旧版保持自动投递关闭。旧版执行器仅认识审核轮次。重新部署 F 版后核对暂停期间的政策、分工和批次变化及仍在办的指派，再决定恢复范围。完整现场闭环和目标库核对完成后方可登记正式切换。
