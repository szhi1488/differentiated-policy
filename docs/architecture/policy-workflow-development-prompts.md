配合[开发技术设计书](policy-workflow-feishu-technical-design.md)使用。A–E（P01–P26）已完成本地开发。E 阶段的隔离验证、配置与目标环境待办见[飞书投递交付记录](policy-workflow-phase-e.md)。F 阶段 P27–P31 已完成开发和本地回归，P33 切换手册已交付。[F 阶段交付与切换手册](policy-workflow-phase-f.md)

申请人在「确认政策适用范围」逐段选单。服务端汇总本轮各确认段实际叠加的所有政策。确有叠加，且各参与单整单实际勾选的具体商品 ID 集合完全相同，整轮才由产品运营初审。其余轮次直接给采购。采购从管理员「差异化政策」完成终审。管理员分别配置两组人员，采购组限本企业有效管理员。[现行分流示例](policy-workflow-feishu-technical-design.md#classification)

进入初审时机器人向本轮每名运营私发一张交互式初审卡，支持通过或填写原因后拒绝。首个有效决定随 ERP 事务提交后，机器人向本轮合格采购私发办理卡，或向原申请人私发退回原因。其余运营的卡片显示「同组他人已处理」。采购终审通过后，业务群收到该轮获批政策公告。后台自动投递受 `POLICY_REVIEW_DELIVERY_ENABLED` 控制。[配置与联调边界](policy-workflow-phase-e.md#环境配置与目标库)

1. **结构改动按范围确认。** 2026-11-23 用户同意按 P01 范围改库并继续 B 阶段。P06–P07 据此交付七张工作流表、按轮切换标记和十五表库的增量升级。2026-11-24 E 阶段另获准扩展投递动作的收件人约束。F 阶段另获准以保留数据的方式扩展独立业务群提醒。[F 阶段升级](../sql/upgrade_workflow_execution_notices.sql)。前两次授权的范围及相应脚本分别见 [B 阶段已有库升级](../sql/database-design.md#已有库升级政策审核工作流) 和 [E 阶段已有库升级](../sql/database-design.md#已有库升级飞书审核卡投递)。

## E　接入飞书私聊初审卡、群通知与个人待办

**现行分流。** 收集每个最终同时采用两单及以上的确认段涉及的政策，合并成整轮参与名单。逐单汇总所有平台的普通卡、指定卡所选商品 ID 并去重。全部集合完全相同且存在叠加，才发运营卡。即使一段的 A、B 完全相同，另一叠加段纳入商品不同的 C，整轮也直接交采购。若 C 未选或一直仅被单独采用，则按 A、B 比较。重提重新判断，旧轮保留原冻结结果。

## 适合停下来看的三个结果

- **P05 后看话术。** 选两张整单商品 ID 完全相同的政策，仅在一个平台的同一确认段同时采用。对照运营私聊卡摘要与按轮详情，核对单号、时段、商品和两单各自的补贴。
- **P22 与 E 阶段联验。** 在管理后台选好两组成员，申请人提交一轮只有两张政策参与叠加且整单商品 ID 完全相同的申请。由一名产品运营在飞书卡上退回，原申请人修订重提后换另一人在卡上通过，再由一名采购在「差异化政策」批准。每节点只记录一名实际决策人，可见其他任务的结办原因。
- **P32 后看真实飞书效果。** 本轮仅有两张政策参与叠加，且二者整单商品集合完全相同时，运营各收一张私聊卡。一人通过后，其他人的卡更新为「同组他人已处理」，合格采购各收办理卡和终审待办。另用一轮验证拒绝后原申请人私收退回原因及修改待办。采购批准后核对群内政策公告。
