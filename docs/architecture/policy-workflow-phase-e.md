## 各节点的收件人与回执

| ERP 事件 | 飞书动作 |
| --- | --- |
| 进入产品运营初审 | 每个有效指派一张可办理卡。卡内列出确认段的时段、商品、原拟采用名单，以及随单调整的目标、原新截止与原因。大单分别显示两类摘要及省略数量，可按轮打开完整详情。 |
| 初审通过 | 两类卡面分别显示实际办理结果与「同组他人已处理」。业务群收到一条含单号、办理人和结果的消息，按发送时仍在办的合格采购逐人 @。每个采购指派有独立 Task V2 待办。 |
| 初审拒绝 | 去除首尾空白后，原因须为 1 至 512 字。结果群消息点名原申请人，原申请人收到修改待办。该轮的个人初审卡变为只读。 |
| 直达采购、终审或重提 | 直提时群内通知采购并逐人建待办。采购终审产生本节点唯一的结果登记，按各指派的 GUID 结办。退回后的修改待办在成功重提交时结办。Task V2 的勾选状态只影响外部任务。 |
| 在途改派 | 保留者沿用原卡或待办，移除者立即失去相应办理权，原卡更新为已改派或原待办结办。新加入的当前成员按全新指派收件。未来采购成员的待办等到终审节点建立时再发。 |

卡片回调核验成功后，由 ERP 提交本轮产品运营初审事务。HTTP 入口核对签名、时效和验证令牌；长连接使用应用凭证连接飞书。两种入口均校验应用、企业、实际点击人、消息回执、指派序号、轮次、节点及版本。改派其他成员后，保留者仍可用原卡办理。重复回调只读取已落库决定。

## 投递与恢复

- 业务事务登记每个动作。后台用限时租约领取，HTTP 往返期间释放数据库锁，最多尝试五次。私聊卡和群消息保存各自的消息 ID，个人待办保存任务 GUID。所有重试沿用企业、单据、轮次、事件、动作和指派派生的同一个幂等标识。
- 创建前记录实际目标与请求摘要。结果未知时，群消息和卡片最多在首次尝试后 55 分钟内自动重试，建任务为 4 分钟，各自给平台的幂等窗口预留余量。超窗、内容或目标变化会转人工核对。进程中断或租约过期后可处理迟到的确定回执。
- 结束节点的创建动作会重新核验。已送达的卡按原消息更新，任务按原 GUID 结办；结果未知时，后继更新等待本人原创建回执。已结束的轮次保留决定和快照。
- 管理员在「系统管理 → 政策审核设置 → 飞书投递记录」输入政策单号和轮次，核对指派、动作、状态、错误及外部回执。已处理项不随其他失败项重发。已送达但丢失回执时，填入飞书消息 ID 或任务 GUID，服务端核验归属再入账。已核实未送达或可安全重试时可重新入队，需填写核对依据。每次人工处理都记录管理员、时间、原状态和依据。[管理接口](../api/policy-review-settings.md#飞书投递记录与人工核对)

## 环境配置与目标库

1. 已有 B 阶段二十二表库先停写备份，由用户在 Navicat 执行[单条收件人约束升级](../sql/upgrade_policy_review_delivery_cards.sql)，核对前后行数相等、检查约束启用并包含两种个人卡片动作。新空库使用本版基线。[数据库核对步骤](../sql/database-design.md#已有库升级飞书审核卡投递)
2. 在同一企业自建应用配置机器人、可用人员及 IM 发送与消息读取权限。启用群通知时配置 `FEISHU_POLICY_CHAT_ID`、机器人群成员资格和 `im:chat.members:read`。群 ID 可留空用于单卡验证，此时需要发群的登记会提示配置问题。使用个人待办时配置 Task V2 任务读写权限。`FEISHU_POLICY_ERP_URL` 填飞书客户端可访问的 ERP 前端根地址。PC、iOS、Android 的待办链接按办理用途选择页面，并携带申请 ID 和提交轮次。[环境参数](environment-configuration.md) · [发送消息](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/create) · [群成员读取](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/chat-members/get) · [Task V2](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/task-v2/task/overview)
3. 在飞书开发者后台订阅 `card.action.trigger`。内网运行可选择下节的长连接。选用加密 HTTP 回调时，配置 `FEISHU_CALLBACK_VERIFICATION_TOKEN`、`FEISHU_CALLBACK_ENCRYPT_KEY`，将公网 HTTPS 的 `POST /callbacks/feishu/policy-review` 精确转发到后端，并保留原始正文及 `X-Lark-Request-Timestamp`、`X-Lark-Request-Nonce`、`X-Lark-Signature` 请求头。旧卡超过平台可交互或更新期限时，管理员可在 ERP 查看本轮审核状态和投递记录，核对仍待处理的指派。[飞书回调接收](https://open.feishu.cn/document/event-subscription-guide/callback-subscription/receive-and-handle-callbacks) · [卡片交互](https://open.feishu.cn/document/feishu-cards/configuring-card-interactions)
4. 每次提交与重提均按轮分流。`POLICY_REVIEW_DELIVERY_ENABLED` 控制外部投递调度，默认关闭。轮询间隔 `POLICY_REVIEW_DELIVERY_POLL_MS` 默认 3000 毫秒。改动部署配置后重启相应实例。当前可由用户按下文验证指定的一张私聊卡。P32 的全流程联调另行核对试点成员、测试群、目标 MySQL、实际群通知与手机回跳。

### 内网自动发卡与卡上审核

内网部署可持续使用长连接。常规 ERP 后端主动连到飞书开放平台，接收按钮回调，无需公网域名。将 `FEISHU_POLICY_CALLBACK_MODE=long_connection` 写入实际后端配置，沿用该自建应用的 App ID、App Secret 和企业标识。本次内网入口填 `FEISHU_POLICY_ERP_URL=http://172.50.50.32:5173`，在 `FEISHU_ALLOWED_ORIGINS` 现有列表中加入 `http://172.50.50.32:5173`。飞书后台选择长连接后无需填开发者服务器请求地址；回调 Encrypt Key、Verification Token 在本模式可留空。更换内网主机或前端端口时，按实际入口更新这两处地址。

管理员先在 ERP 保存两组审核人员。日常自动投递使用 `POLICY_REVIEW_DELIVERY_ENABLED=true`，后台每次启动都会处理符合条件的待发记录。仅自验一张卡时按下一节关闭常规服务的自动投递。首提和重提自动按轮分流，已移除的 `POLICY_REVIEW_WORKFLOW_ENABLED` 无需配置。

1. 在 IDEA 中重新加载 Maven 工程并重启新版后端，或启动本次构建的 Spring Boot JAR。看到日志「飞书卡片回调长连接已建立」后，保持后端在线。
2. 在同一应用的「事件与回调 → 回调配置」选择「使用长连接接收回调」并保存。保留「卡片回传交互」`card.action.trigger`；正式应用按控制台提示发布配置。[飞书回调说明](https://open.feishu.cn/document/event-subscription-guide/callback-subscription/receive-and-handle-callbacks)
3. 用一个进入产品运营初审的新轮次验证。机器人自动把私聊卡发给当前指派，审核人在卡上通过或填写原因退回。飞书将决定经长连接交给 ERP；查看完整详情时，客户端需要能访问公司网络。管理员可在「政策审核设置 → 飞书投递记录」核对各项回执。

切换模式后，待投递的有效动作由后台继续领取。旧记录已明确失败时，先核对失败原因及送达情况，再使用管理员页面的重新入队操作。已失效的指派保留原记录。

### 内网发送一张初审卡

以用户自行验证 Becca 的 `ZC-000033` 为例。该单的数字申请 ID 是 `33`。实际提交轮次、当前阶段、收件指派和送达情况以 ERP 投递记录为准。

1. 仅验证这一张时，将使用该开发库的常规后端配置为 `POLICY_REVIEW_DELIVERY_ENABLED=false`。由用户重启常规后端，确认已建立长连接，并在飞书开发者后台保存长连接回调配置。测试期间保持该后端在线。
2. 在「差异化政策」核对该申请的实际提交轮次、当前阶段和 Becca 的有效指派。在「系统管理 → 政策审核设置 → 飞书投递记录」按 `ZC-000033` 和该轮次查询。仍待运营初审时，找到收件人为 Becca 的「发送初审卡」动作（`SEND_CARD`），复制该行的完整投递编号（`deliveryKey`，UUID）。若没有该行，先核对轮次、分流和指派。若显示「已送达」且有消息 ID，可直接核对收件。若显示「结果待核对」或「投递失败」，先按[投递与恢复](#投递与恢复)核对。
3. 由用户在 `backend` 目录运行本次构建的 JAR。按投递记录输入实际轮次及编号。

```powershell
$round = Read-Host '输入已核对的提交轮次'
$deliveryKey = Read-Host '粘贴 Becca 的发送初审卡投递编号'
java -jar target/policy-0.0.1-SNAPSHOT.jar send-review-card 33 $round $deliveryKey
```

命令独立启动，处理指定登记后退出。服务端校验该轮指派和投递状态，成功后原登记显示「已送达」（`SENT`）及飞书消息 ID。重复指定已发送的卡会返回已有回执。Becca 可在与机器人的私聊中核对单号、轮次和摘要。「查看本轮详情」打开内网只读页。「通过」和填写原因后的「拒绝」会实际提交决定。关闭自动投递期间，常规后端仍能经长连接接收点击，后续卡面更新、群通知及待办保留在队列中，恢复自动投递后才会发出。该示例的真实发送、点击及回执由用户现场验证。
