## 当前页面实现与目标规则的边界

2026-11-11 申请页已改用 Element Plus，通用控件、表格和提示的替换不改变本文业务规则。渠道使用 Select，平台使用 CheckTag，核销类型/场景/预估标记使用 Radio，明细平台使用 Tabs，机型明细使用 Table。切换渠道、取消已填写平台及清空表单通过 MessageBox 等待用户确认，选择保留时不改原值。菜单切换继续保留已填内容。

日期范围使用 DatePicker，页面状态保存 `YYYY-MM-DDTHH:mm:ss` 字符串，清空同时清空起止值；按北京时间解释，避免浏览器时区自动转换。金额输入保持字符串。手机宽度下完整显示两个时间，日期弹层纵向滚动；明细表格横向查看并固定右侧操作列。

当前标准目录接口尚未接入，型号/配置/颜色仍为手工输入占位，尚无正式的标准规格选择和 `ALL_COLORS` / `SPECIFIC_COLOR` 交互；后文对应规则为接入时必须遵守的目标要求。附件 Upload 设置 `auto-upload=false`，选择、拖放及移除仅影响当前页面，不调用已存在的独立附件接口；备注、说明和链接仍是页面状态。提交显示“政策提交功能尚未接入，当前填写内容未提交”，我的提交仍为占位页。组件替换不表示完成草稿、提交、审核或上传联调。

2026-11-11 规范化重构：`layouts/ApplicantLayout.vue` 持有并提供 `usePolicyForm`，基础信息、时间、明细和附件区块通过事件表达修改意图，不深层修改父级业务对象；明细按稳定 key 更新，渠道/平台确认及补贴互斥集中管理。申请人使用 `/apply`、`/apply/submissions` 命名路由，切菜单保留内容；退出、会话失效或账号/租户/角色变化时清理表单与暂存附件，不增加浏览器持久化。价格基数编码沿用数据字典的 `HAND_PRICE`、`LOCAL_ACTUAL` 等值；表单、展示模型分离，当前不发送业务 DTO，也不为手工机型生成标准目录 ID。

本轮 `npm.cmd run check` 通过 19 个测试文件的 77 项测试及 lint、格式和构建；已检查 1440/768/390px 隔离预览的日期、表格、菜单保留和取消回显。详细记录见 [前端规范](../architecture/frontend-development.md#9-验证记录与维护) 和 [整体架构](../architecture/system-overview.md#前端组件与页面现状)。浏览器预览不代表真实飞书授权或政策接口联调。

## 渠道与平台

申请人默认进入「提交政策」，侧栏「政策提交 → 提交政策 / 我的提交」。同一表单选择渠道，不设视角页签；顶部无搜索、消息、头像。

| 项目 | 零售 | 百亿 |
| --- | --- | --- |
| 渠道 | 零售渠道 | 百亿渠道 |
| 平台 | 快手、拼多多、京东、抖音、天猫、淘宝、招商、得物、联通、政企 | 拼多多、淘宝、联通 |
| 平台选择 | 单选、多选、全部 | 单选、多选、全部 |
| 核销类型 | 销售维度 / 激活维度，二选一 | 不适用 |
| 场景 | 国补 / 地补 / 自补，单选 | 不适用 |
| 预估政策 | 是 / 否 | 不适用 |

保留“招商”等名称，不替换或合并。“全部”是操作，保存明确集合，不保存 `ALL`；未来新增平台是否适用历史全选政策待确认，不自动扩展。

渠道切换同步选项；百亿核销类型、场景、预估标记为 `NULL`，不把“不适用”保存为“否”。后端拒绝跨渠道平台与字段。当前切换会清空平台和明细，已有平台时先提示确认；取消已填写平台也提示，数量 0 仍视作已填写。

## 明细粒度与顺序

1. 选择渠道、平台。
2. 在具体平台下选择品牌、系列、型号及配置，然后明确不限颜色或指定该规格下具体颜色；数量选填。
3. 填写该平台各机型的补贴方式及参数。
4. 填政策时间、备注和附件/链接，保存或提交。

政策时间精确到北京时间秒。数量可 NULL、不自动填 0，零值含义仍待确认。颜色范围必须显式选择：ALL_COLORS 表示当前型号配置不限颜色，商品 ID/颜色名称快照为 NULL；SPECIFIC_COLOR 正式提交必须有当前规格下有效商品 ID 和服务端名称快照。color_scope=NULL 仅为未完成草稿，不解释成不限颜色。

不同型号、同型号不同配置各自维护颜色；颜色下拉仅查当前配置的 ACTIVE 商品，切换规格清空旧颜色，后端以复合关系检查。一个指定颜色保存一条明细，多颜色分别保存；同平台同规格不限颜色与指定颜色交集须提示整理，不能静默最后一条取胜。跨政策的优先级和替换规则仍待确认。

同机型跨平台可不同补贴，也可部分/全部已选平台共享。共享在界面批量维护，保存展开为各平台明细；数量仍属各平台，不能随共享补贴复制。

例如同机型拼多多数量 100、固定 50，淘宝数量留空、比例 10%，应保存两条明细，不合并主表补贴，不把淘宝数量补成 100。示例仅解释结构，不是初始化数据。

每条明细平台须属于已选集合。重复冲突按稳定 spu_id、ram、rom、color_scope、goods_id 及平台识别，名称快照不作唯一身份。

## 补贴互斥

| 方式 | 相关字段 | 必须清空 |
| --- | --- | --- |
| 固定 `FIXED` | 固定金额、补贴上限 | 比例、计算基数 |
| 比例 `RATIO` | 比例、计算基数 | 固定金额、补贴上限 |

基数选项为零售价、政策价、到手价、地补实际、商家配控，保留名称，真实取值来源待确认。切换清理另一组参数，前后端校验互斥；草稿允许当前方式字段暂缺。

金额 `DECIMAL(10,2)`，比例 `DECIMAL(5,2)` 百分数（10.00 表示 10%），Java `BigDecimal`，禁浮点计算金额。SQL 只约束非负，不等于允许 999.99% 或已设 100% 上限。最终范围、精度、舍入和固定上限作用范围待确认。

## 主数据与附件

- 吉客云同步一加和 OPPO，先按 SKU 保存原文，再按受控规则识别系列、型号、配置和颜色。唯一明确且校验通过时自动创建或复用规格颜色，缺失、歧义和冲突由人工审核。新基线将已确认的配置和颜色写入 goods，来源保留候选并记录 goods_id。[自动清洗](catalog-cleaning.md)
- 空库 SQL 保存机型、RAM、ROM、指定颜色商品及品牌系列与型号配置快照。正式提交由服务端核验 ACTIVE 及归属并生成快照，目录改名或停用不改写已提交政策。
- 不纳入“吉客云政策名”，不回写吉客云，不把图中机型或用户举例写成真实种子数据。商品同步与标准目录尚未实现。
- 支持特别备注、上传或链接；必填、数量、存储、类型大小、下载鉴权和链接规则待确认。当前文件只在前端选择，未上传。
- 前端 `remark`、`explanation`、`links` 是页面状态；接入时明确如何映射 `special_remark`、`attachment_info`，不得静默丢弃说明或链接。

## 草稿与提交

草稿至少有服务端单号、申请人和渠道，可不选平台、不建明细；时间、机型和补贴字段可暂缺，已填写内容仍校验类型和互斥。

正式提交须有平台、起止时间及完整明细，标准规格、明确颜色范围、型号配置快照、补贴方式和参数完整；指定颜色时必须有该规格下商品 ID 和颜色名称快照，零售分类字段必填。每个已选平台是否至少一条完整明细、固定上限是否必填、备注附件要求仍待确认，不擅自增加门槛。

当前只有表单交互；服务端完整校验、共享批量编辑及持久化待实现。见 [状态机](status-machine.md) 和 [接口草案](../api/policy-api.md)。
