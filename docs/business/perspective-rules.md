# 零售与百亿动态表单规约

更新日期：2026-11-14。依据原业务文档及用户最新确认；存储细节见 [数据字典](../sql/database-design.md)，商品与数据库结构见 [确认方案](../architecture/catalog-admin-design.md)。业务规则确认不表示持久化接口已实现。

## 当前提交页面

申请人从「政策提交 → 提交政策」进入 `#/apply`，按基础信息、政策时间与详情、商品及补贴信息、其他信息填写。同一表单切换零售与百亿。商品读取 `goods` 在售目录。草稿保存、链接回填和正式提交已接入，管理员审核和申请页附件上传待接入。

### 选商品与配置

| 入口 | 选择方式 | 加入政策后的填写方式 |
| --- | --- | --- |
| 左侧「指定适用机型」 | 每次单选一件带具体颜色的在售商品，按商品 ID 防重复 | 每件商品独立成卡，显示具体颜色，隐藏标准 SKU。各平台数量选填，可留空 |
| 右侧「选择手机型号」 | 按配置筛选，复选具体在售商品并保存各自的商品 ID | 所选商品共用一张普通卡，统一填写适用平台与补贴。普通卡无数量输入 |

- 按钮和抽屉标题使用同一名称。两个抽屉共用品牌、系列、机型、配置四级联动筛选，切换上级条件时清除已不匹配的下级值。两个列表均为全宽单列，每行显示品牌、系列、机型、内存配置和颜色。
- 配置可多选，也可点「全部配置」选取当前品牌、系列和机型范围内的所有配置。普通卡默认跨页勾选所选配置下的全部在售商品。移除配置会取消该配置在本次抽屉中的勾选。手动取消的商品在翻页、搜索和切换配置后保留取消状态。指定适用机型可用同一筛选，商品仍单选。
- 商品卡按机型版本分行，显示「品牌 / 系列 / 型号」，同一行列出适用配置。跨系列、跨品牌沿用同一格式。补选或移除部分普通配置保留已填补贴；普通卡和指定适用机型卡可同时存在。

### 平台与补贴

- 在「基础信息」选择整单平台。普通卡和指定适用机型卡默认沿用整单平台，整单新增平台时自动带入。卡片先显示当前适用范围，点击「调整平台」展开勾选并可缩小范围。自行调整的卡片不会自动接收后来新增的整单平台；「恢复整单平台」重新启用联动。
- 适用平台和补贴方案分别维护。新卡提供「方案 1」，选中的平台默认共用；添加其他方案后可为各平台单独分配。指定适用机型的数量独立填写，不随补贴方案共享。清除会丢失的表单内容前按页面确认流程处理。

### 本地状态与提交边界

- 日期精确到北京时间秒，保存为 `YYYY-MM-DDTHH:mm:ss` 字符串。清空日期范围同时清空起止值。金额保持十进制字符串。
- `ApplicantLayout.vue` 持有 `usePolicyForm`，区块通过事件表达修改意图，明细按稳定 key 更新。往返「我的提交」保留表单；退出、会话失效或账号、租户、角色变化时清除表单和暂存附件。已保存申请可通过 `#/apply?policyId=<id>` 刷新回填。
- 附件文件只在本地暂存。点击「保存草稿」后以当前申请地址恢复本人草稿或驳回申请。点击「提交申请」先保存表单，再使用返回的版本号提交。提交成功后显示待审核并锁定表单。「我的提交」支持按状态、渠道和整单平台筛选，详情可查看历轮审核结果和各轮提交快照。草稿和已驳回申请可继续编辑，待审及已通过申请可查看详情。打开其他申请前若有未保存内容，取消确认会保留当前表单和暂存附件。

前端检查及浏览器验收记录见 [前端规范](../architecture/frontend-development.md#9-验证记录与维护) 和 [整体架构](../architecture/system-overview.md#前端组件与页面现状)。

## 渠道与平台

申请人默认进入「提交政策」，侧栏「政策提交 → 提交政策 / 我的提交」。同一表单选择渠道，不设视角页签；顶部无搜索、消息、头像。

| 项目 | 零售 | 百亿 |
| --- | --- | --- |
| 渠道 | 零售渠道 | 百亿渠道 |
| 平台 | 快手、拼多多、京东、抖音、天猫、淘宝、招商、得物、联通、政企 | 拼多多、淘宝、联通 |
| 平台选择 | 单选、多选、全部 | 单选、多选、全部 |
| 核销类型 | 销售维度 / 激活维度，二选一 | 不适用 |
| 场景 | 国补 / 地补 / 自补，单选 | 不适用 |
| 预估政策 | 是 / 否 | 不适用 |

保留“招商”等名称，不替换或合并。“全部”是操作，保存明确集合，不保存 `ALL`；未来新增平台是否适用历史全选政策待确认，不自动扩展。

渠道切换同步选项；百亿核销类型、场景、预估标记为 `NULL`。正式接入后由服务端拒绝跨渠道平台与字段。当前切换会清空平台和明细，已有平台时先提示确认；取消已填写平台也提示，数量 0 仍视作已填写。

## 后端持久化方案

草稿写入 `policy_apply.goods_form_json`，保存两类卡选中的商品 ID、卡片类型、平台联动、补贴方案及平台分配。审核和历史从 `policy_audit_log.snapshot_data` 回读本轮提交内容。普通卡数量为空，指定卡数量按平台选填。

政策时间精确到北京时间秒。数量可为 NULL，零值含义待确认。两类卡提交时均须传实际勾选的商品 ID，由服务端核验商品在售、配置归属并生成显示快照。

例如同一配置在售黑色和白色，选配置后会默认勾选两件。取消白色后，正式提交只保存黑色的商品 ID，后续新增颜色也须重新选入适用范围。同一平台下，普通卡和指定卡选中同一个商品时须提示整理。

同机型跨平台可使用不同补贴，也可部分或全部平台共享。共享方案展开时各平台保留各自的数量。

例如同一指定颜色商品，拼多多数量 100、固定补贴 50 元，淘宝数量留空、比例 10%，分别形成两条平台明细，淘宝数量保持为空。示例仅解释结构。

每轮提交从同一份表单按实际平台和选中商品生成 `policy_goods_detail`，每条保存轮次、平台、商品 ID 及所属机型版本、RAM、ROM。每条明细平台须属于整单平台，按平台和商品 ID 从该轮快照定位补贴及数量。

## 当前补贴互斥规则

| 方式 | 相关字段 | 必须清空 |
| --- | --- | --- |
| 固定 `FIXED` | 固定金额、补贴上限 | 比例、计算基数 |
| 比例 `RATIO` | 比例、计算基数 | 固定金额、补贴上限 |

基数选项为零售价、政策价、到手价、地补实际、商家配控，保留名称，真实取值来源待确认。切换清理另一组参数，前后端校验互斥；草稿允许当前方式字段暂缺。

金额 `DECIMAL(10,2)`，比例 `DECIMAL(5,2)` 百分数（10.00 表示 10%），Java `BigDecimal`，禁浮点计算金额。SQL 只约束非负，不等于允许 999.99% 或已设 100% 上限。最终范围、精度、舍入和固定上限作用范围待确认。

## 实单与待确认口径

用户提供的实际提交表中，天猫与淘系共用一加 Ace7 Pro 的五个配置，补贴比例 9%，补贴上限 450 元；京东示例同时填写 10% 和上限 500 元。另有京东记录只填写上限 550 元。实单支持多平台、多配置共用补贴，也表明「比例与上限同时填写」需要在后续接入前纳入设计评估。当前表单和后端沿用上表约定，比例方式尚不能填写上限。新三表通过方案 JSON 表达补贴和上限，正式校验及计算按确认后的业务口径实施。

- 明确比例上限的单位、作用范围、必填性和校验，以及仅填写上限代表的业务含义。
- 核对实单平台文案与系统已选平台编码的映射，避免从截图直接增删或合并平台。

## 主数据与附件

- 吉客云同步一加和 OPPO，先按 SKU 保存原文，再按受控规则识别系列、型号、配置和颜色。唯一明确且校验通过时自动创建或复用规格颜色，缺失、歧义和冲突由人工审核。新基线将已确认的配置和颜色写入 goods，来源保留候选并记录 goods_id。[自动清洗](catalog-cleaning.md)
- 空库 SQL 保存每轮商品 ID、机型、RAM、ROM 及完整提交快照。服务端核验商品状态和配置归属后生成快照，目录改名后已提交政策仍按该轮快照回读。
- 管理端已接入标准目录查询与维护，申请页读取同一套在售目录。实单只作为需求依据，不写入种子数据。吉客云维持只读。
- 支持特别备注、上传或链接；必填、数量、存储、类型大小、下载鉴权和链接规则待确认。当前文件只在前端选择，未上传。
- 前端 `remark`、`explanation` 分别映射 `policy_apply.remark`、`other_desc`。链接及上传后的文件 ID 保存到 `attachment_urls`，元素规则见附件方案。

## 草稿与提交

草稿至少有服务端单号、申请人和渠道，可不选平台、不建明细；时间、机型和补贴字段可暂缺，已填写内容仍校验类型和互斥。

正式提交须有平台、起止时间及完整商品卡，校验实际选中的商品、配置归属、补贴方式和参数，并生成商品快照。零售分类字段必填。每个已选平台是否至少一条完整明细、固定上限是否必填、备注附件要求仍待确认。

服务端保存草稿，正式提交时复核在售商品、配置和字段完整性，按平台及最终所选商品写入明细和本轮快照。见 [状态机](status-machine.md) 和 [申请人接口](../api/policy-api.md)。
